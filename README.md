# 新产品可行性评估报告

**产品名称**：中小型电商 AI 客服产品（暂定名）
**评估阶段**：立项前可行性评估
**报告性质**：基于业务分析与技术分析两份输入的综合评审意见
**编制说明**：本报告严格区分「已知信息」「分析判断」「待验证假设」三类内容；未引用任何未经提供的业务数据或测试结果。


## 一、项目背景与目标

### 1.1 已知信息（来自原始需求）

- **产品构想**：为中小型电商企业开发 AI 客服产品，处理商品咨询、订单状态查询、退换货政策查询、售后问题四类场景。
- **推进方式**：初期先服务少量试点商家，要求控制开发成本。
- **演进要求**：后续需接入商家的订单系统、商品系统和知识库。
- **数据现状**：**尚无**准确的客户数量、预算和业务效果数据。
- **本次诉求**：评估是否值得进入下一阶段的立项评审。

### 1.2 分析判断

需求方向明确，但**需求明确度整体偏低**：场景边界相对清晰（四类咨询），但缺少可量化目标（响应时长、自助解决率、准确率门槛）、缺少客户规模与预算约束、缺少效果基线。这意味着当前不具备做投入产出测算的条件，任何"值得/不值得"的绝对结论都缺乏数据支撑。

### 1.3 本报告的目标

不是回答"这个产品能不能成"，而是回答一个更窄、更可操作的问题：**在当前信息条件下，是否应批准进入下一阶段，以及下一阶段应该是什么形态、需要补齐哪些数据。**


## 二、业务价值分析

### 2.1 已知信息

- 目标客户为中小型电商企业，客服人力有限、重复咨询多。
- 四类场景中，商品咨询与退换货政策查询对系统集成依赖低；订单状态查询与售后处理依赖订单/商品系统对接。

### 2.2 分析判断（业务价值成立性）

**需求真实性：判断为成立，但属推理而非验证结论。** 依据是中小电商"高频、标准化、可被知识库覆盖"的咨询特征，理论上适合AI 切入。但这是基于行业常识的推断，**尚未经过任何目标客户访谈或需求验证**。

**价值分层判断**：业务分析给出的场景优先级（知识库类优先试点、订单/售后后置）在逻辑上成立，且直接服务于"控制成本"诉求——先做集成依赖低的场景，可用最小成本验证 AI 回答质量。这一分层建议予以采纳。

**商业可行性的关键制约**：产品价值高度依赖"能否低成本接入商家异构系统"这一未验证假设。中小商家系统形态差异大，逐个对接可能侵蚀"低成本"目标。**技术可行不等于商业可行**——即使 AI 回答质量达标，若单商家集成成本过高或商家付费意愿不足，产品商业模式仍不成立。

### 2.3 待验证假设（业务侧）

| 编号 | 假设 | 当前状态 | 验证方式 |
|---|---|---|---|
| B1 | 中小商家愿意且能够开放订单/商品系统接口 | 未验证（最大风险点） | 试点前访谈 + 接口样例获取 |
| B2 | 商家现有知识库足以支撑准确回答 | 未验证 | 索取真实知识文档评估清洗工作量 |
| B3 | 商家愿意付费，且价格敏感度可接受 | 未验证（无定价数据） | 试点期报价测试 |
| B4 | AI 能实际降低人工负担而非仅分流 | 未验证（无基线） | 试点前后人工咨询量对比 |
| B5 | 少量试点下开发与集成成本可控 | 未验证（无预算数据） | 阶段 0 预研实测 |

### 2.4 需要补充的数据

- 目标客户数量区间与可接受预算区间；
- 试点商家现有客服人力成本与咨询量基线；
- 商家可接受的效果阈值（自助解决率/转人工率/响应时延）；
- 竞品定价与差异化定位依据。


## 三、技术实现建议

### 3.1 已知信息

- 工作目录为空，无现有代码或文档可参考，技术分析完全基于需求描述。
- 四类场景在技术上均为成熟可实现，无硬性技术障碍。

### 3.2 分析判断（技术可行性）

**技术可行性：判断为可行。** 方案可由成熟组件组合实现，无需自研模型。但需明确：**技术可行仅说明"能做出来"，不说明"做了划算"**。真正的成本决定项是集成层与治理层，而非模型能力本身。

**关键选型判断（采纳技术分析建议）**：

- **大模型**：必要，商用 API 起步，试点期不自建、不微调（无足够数据，投入产出不成立）。
- **RAG**：必要但要做"轻"，先用成熟向量库 + 简单切分，不做多路召回/重排/知识图谱。
- **工具调用**：必要，订单/物流/工单必须走真实系统，不能靠模型编造。难点不在模型而在商家系统形态。
- **MCP**：当前阶段不必要，直接写适配器更可控，接口设计预留抽象层即可。
- **数据库**：关系库 + 向量检索能力即可，试点期不引入消息队列、数据湖等。
- **明确不做**：自建模型/微调、多智能体编排、复杂工作流引擎、自研向量库、全渠道中台。

**必须第一版就做的治理能力**：多租户数据隔离、基础 RBAC、工具调用最小权限、答案溯源 + 高风险问题强制转人工、会话日志与评测看板、个人信息脱敏。这些事后补代价极高。

### 3.3 待验证假设（技术侧）

| 编号 | 假设 | 当前状态 | 影响 |
|---|---|---|---|
| T1 | 目标商家订单/商品系统有可用 API 或可导出数据 | 未验证 | 直接决定集成成本量级 |
| T2 | 商家接受数据经第三方大模型 API 处理 | 未验证 | 若强制私有化，架构与成本模型需重做 |
| T3 | 商家知识文档可结构化、可导出 | 未验证 | 知识清洗是隐性成本大头，易被低估 |
| T4 | 单会话 token 成本可控 | 未验证 | 决定规模化后毛利 |
| T5 | 自助解决率能达到商家可接受水平 | 未验证（核心） | 产品成立与否的核心指标 |

### 3.4 需要补充的数据

- 目标商家系统形态分布（SaaS 有 API / 自建有 API / 仅后台页面）及比例；
- 商家对数据出境/第三方处理的接受度；
- 试点商家知识库现状样本（结构化程度、更新频率）；
- 渠道优先级（网页挂件 vs 商家现有 IM）；
- 售后场景边界（仅查询/建单，还是参与退款审批等资金决策）；
- AI 错误政策导致损失时的责任划分口径。


## 四、主要风险与待验证假设

### 4.1 风险汇总（按影响排序）

| 优先级 | 风险 | 性质 | 缓解方向 |
|---|---|---|---|
| 高 | 商家系统异构导致集成成本失控 | 商业+技术 | 试点只支持有 API 商家；无 API 走坐席辅助/人工兜底 |
| 高 | 商家拒绝数据经第三方大模型处理 | 商业+合规 | 提前确认；预留私有化选项但不在试点期实施 |
| 高 | 自助解决率不达商家预期 | 商业核心 | 阶段 0 用真实问题做离线评测 |
| 中高 | 回答幻觉引发客诉与商誉损失 | 技术+合规 | 答案溯源 + 高风险强制转人工 + 责任边界约定 |
| 中 | 知识清洗工作量被低估 | 技术成本 | 阶段 0 实测清洗工时 |
| 中 | 付费意愿不足/价格敏感 | 商业 | 试点期报价测试 |
| 中 | 多租户数据隔离缺失 | 技术 | 第一版即做，不后补 |
| 中 | 效果无法衡量导致续费困难 | 商业 | 第一天建立评测与 badcase 回流 |
| 低-中 | 通用客服工具竞争 | 商业 | 差异化定位：电商场景深度 + 轻量集成 |

### 4.2 待验证假设汇总（合并业务与技术）

**最高优先级三项**（任一答案不利都会显著改变方案与成本模型）：

1. **目标商家订单/商品系统是否有可用 API**（B1/T1）；
2. **商家是否接受数据经第三方大模型处理**（T2）；
3. **商家认可的效果验收标准是什么**（B4/T5）。

其余假设（B2、B3、B5、T3、T4）可在阶段 0 与试点 MVP 中逐步验证。

### 4.3 信息不足声明

本报告**未获得**任何客户数量、预算、效果基线、竞品定价、商家系统形态分布数据。上述所有"分析判断"均为基于需求描述的推理，**不构成已验证结论**。在补齐 4.2 三项最高优先级数据前，不应做重投入决策。


## 五、建议的实施阶段

采纳两份分析中一致的分阶段思路，建议如下：

### 阶段 0：技术预研（建议 2–4 周，低成本）

- **目标**：验证可行性，不追求产品化。
- **动作**：选 1–2 家高配合度商家，获取真实知识文档与订单接口样例；做端到端最小原型（单渠道 + RAG + 1 个订单查询工具 + 转人工）；用真实历史会话或构造 50–100 条问题做离线评测。
- **产出**：带数据的可行性报告（初步解决率、幻觉率、单会话成本、知识清洗工时），作为正式立项评审输入。
- **决策点**：三项最高优先级假设是否得到初步正面答案。

### 阶段 1：试点 MVP（试点商家 3–5 家）

- 单渠道接入、单商家适配器模式、租户隔离、基础后台、日志与评测看板。
- 明确只支持有 API 商家，无 API 走坐席辅助模式。
- **目标**：跑通闭环，采集效果与成本数据。

### 阶段 2：能力补齐

- 多商家适配器扩展、知识库自助维护、售后工单闭环、badcase 驱动优化。
- 此时再评估是否需要 MCP、是否需要私有化部署选项。

### 阶段 3：规模化

- 多渠道路由、计费与用量统计、SLA 与稳定性建设。
- **是否进入取决于阶段 1 的效果与成本数据**，当前不做预判。

**阶段准入原则**：每一阶段结束设明确决策点，未达成功标准不进入下一阶段。成功标准的具体数值需在阶段 0 与商家共同定义（即使数字待定，也应先定义衡量口径）。


## 六、是否建议进入下一阶段评审

### 6.1 结论

**建议"有条件进入下一阶段"，但下一阶段应定位为「阶段 0 技术预研 + 试点方案评审」，而非「全面产品开发立项」。**

### 6.2 判断依据

**支持进入的依据**：
- 需求方向真实，四类场景边界相对清晰，属"高频、标准化、可被知识库覆盖"的适配场景（分析判断）；
- 技术上无死结，可用成熟组件低成本组合实现（分析判断）；
- 场景分层（知识库类优先、订单/售后后置）与"控制成本"诉求一致，存在低成本验证路径。

**不支持直接全面立项的依据**：
- 客户数量、预算、效果三类关键数据全部缺失，无法做投入产出测算；
- 产品价值高度依赖"低成本接入异构系统"这一未验证假设，且该假设是最大风险点；
- 技术可行 ≠ 商业可行，付费意愿与效果阈值均无数据；
- 若现在直接评审全面开发，最可能的结果是"因缺少效果与成本数据而无法决策"。

### 6.3 通过条件（评审需明确）

1. 批准阶段 0 预研预算与时间盒（2–4 周）；
2. 明确试点商家数量范围（建议 3–5 家）与筛选标准（优先有 API、配合度高）；
3. 定义三项最高优先级假设的验证口径与成功标准；
4. 明确可接受的单商家集成成本上限；
5. 明确数据合规底线（是否接受第三方大模型处理、责任划分口径）。

### 6.4 暂缓/重估条件

若阶段 0 或评审中发现以下任一情况，应重新评估产品形态（如退化为纯知识库轻量版或坐席辅助模式），而非继续按原方案推进：

- 目标商家普遍无法开放系统接口；
- 商家普遍拒绝数据经第三方处理且私有化成本不可接受；
- 付费意愿明显不足或可接受价格远低于成本；
- 离线评测显示自助解决率显著低于商家可接受阈值。

### 6.5 一句话结论

**方向值得做，但当前证据不足以支撑重投入；建议以「批准阶段 0 低成本预研」作为本次评审的决策项，用带数据的预研结果再决定是否进入正式产品立项。**


**附：本报告未编造任何业务数据或测试结果；所有数值区间（如 2–4 周、3–5 家、50–100 条）均为建议性方案参数，非实测结论，需在评审中确认。**
